# 交易复盘项目｜阶段二冻结起点

本仓库保存的是这个项目截至阶段二冻结时的正确起点，以及阶段二冻结以后重新整理、用于让新窗口正确理解项目的接管说明。

它的作用是让新的 Chat 窗口和以后获得具体授权的干净 Work 执行窗口能够从同一份稳定材料开始，不再依靠用户反复搬运文件和口头补充历史。

本仓库不是旧工程的继续运行版本，也不是已经建好的客观交易链，更不是阶段三、业务修复、重新计算、一百三十六笔构建或正式交易分析的执行授权。

## GitHub正式版、待检查稿和附件怎样分开

本项目长期采用以下共同读取方式：

- `main`正式主线只保存已经由用户最终验收、并且另行授权并入的正式版本。
- 尚未获得用户最终验收的修改稿，只放在一条与当前任务对应的待检查分支；待检查分支中的内容是候选，不会因为已经上传就自动成为正式事实或正式版本。
- 新 Chat检查正式版本或候选版本时，默认通过已经连接的GitHub插件读取用户指定的完整提交编号。正式接管读取正式主线的固定提交；候选检查读取待检查分支的固定提交。只给分支名称、文件名、最新页面或会继续变化的地址，都不能代替完整提交编号。
- 如果候选检查不通过，在同一条待检查分支继续定点修正并形成新的固定提交，不在窗口之间反复复制、粘贴或上传完整正文，也不为每次修正另造一套文件。
- 只有GitHub插件发生真实读取失败、失败对象和原因已经说清，而且用户明确同意使用附件时，才把完整附件作为该次读取的临时备用办法。附件不能静默取代GitHub正式来源。
- 用户最终验收候选以后，仍须另行明确授权，候选才可以并入`main`正式主线。任何创建分支、修改、提交、上传、合并或删除，都必须有用户对该次动作和文件范围的明确授权。

待检查分支不会改变正式主线当前保存的事实。任何窗口说明“当前正式状态”时，必须以用户指定的正式主线固定提交为准；说明“正在检查的候选”时，必须同时标明候选固定提交和它所依据的正式主线起点，不能把两者混为同一版本。
