# 两份母版对照与六份历史聊天完整正反查证方案
## 最终执行方案候选，待用户确认

这份方案已经合并双方经复核后保留的做法，并处理了前两轮交流中需要收紧的地方。它是一项工作的完整安排，下面的步骤不是新增的正式项目阶段。

**当前只形成方案，不代表开始执行，也不产生文件修改、提交上传或后续业务权限。**

## 一、本次究竟要查清什么？

本次工作的目的，是查清：

> 两份十笔母版已经呈现了哪些客观交易内容，这些内容是怎样形成的、依靠什么材料，阶段一、二、三已经交代了什么，以及完整历史中是否还有尚未交代清楚的相关内容。

具体回答六个问题：

1. 两份母版分别具备哪些客观交易链内容和能力？
2. 这些内容依靠哪些数据、文件、工作表、字段、公式、算法或截图形成？
3. 两份母版之间发生了哪些变化，变化的原因和实际影响是什么？
4. 阶段一、二、三已经把哪些内容及其来源说明清楚，哪些只是尚未建立明确对应？
5. 六份完整聊天中，是否还有母版未呈现、现有阶段记录未交代，但确实与客观交易链有关的要求、数据、方法或文件？
6. 经过对照和查证，哪些能够确认已有，哪些存在具体冲突，哪些仍缺少足够证据？

**不预先假定以前一定漏扫，也不预先假定两份母版已经包含全部所需内容，更不预先宣布还缺多少项。**

本次仍服务于原有关系：客观交易链帮助人工智能理解真实交易过程，交易分析帮助用户理解自己，最终服务于用户的“彻底改变”。本次不开展交易分析，也不提前判断用户应该改变什么。

## 二、检查哪些材料，哪些不检查？

### 1. 两份十笔母版

分别检查：

- `30天逐笔人工复盘增强版_10笔成品原型_F2.5.4_M4-F2仓位链连续性修正版.xlsx`
- `K08_PC1_RW003_10笔用户产品后置纠偏候选.xlsx`

按照用户的说明，它们是旧工程不同时间的重要十笔母版。“半成品”主要指当时以十笔作为母版，还不是一百三十六笔全部完成的成果，不能直接理解为它们只具备一半能力。

两份表均排除以下两张人工复盘页：

- `逐笔人工复盘总表`
- `人工复盘完成清单`

**排除这两页以后，其余工作表都必须检查，不能由执行者先凭印象挑选“相关页面”。**

剩余页面中仍要区分：

- 可以核对的交易记录；
- 计算或转换产生的结果；
- 用户自述或人工补录；
- 人工评价、心理判断、下次规则等主观内容；
- 只是改变呈现方式的展示内容。

不能因为数据是人工填写，就直接认定它是主观内容；也不能因为它已经写进母版，就直接认定它是经过证明的客观事实。需要说明其实际来源和核验情况。

如果剩余页面引用了已排除的人工复盘页，应标明这种引用，不因此自动把被排除页面重新纳入检查范围。

### 2. 六份旧工程聊天原文

完整检查第一份至第六份历史聊天，即 W01 至 W06。

两遍都覆盖全部原消息：

- 正向：第一份开头，连续到第六份末尾。
- 反向：第六份最后一条消息，连续查回第一份第一条消息。

这次不在旧工程的 K01 启动边界处拆成两个独立扫描任务，但必须保留每件事情实际发生在边界以前还是以后的区别。

### 3. 阶段一、二、三正式冻结成果

将三个阶段已经正式验收冻结的成果作为对照依据，检查其中的组成部分、能力、具体材料、来源、版本、处理结论及限制。

它们是正式记录，不是可以随意重写的草稿；但正式冻结也不意味着不能核对其覆盖范围或报告新发现的证据差异。

**本次不修改、替代、撤销或取消任何冻结结论。**

此前已被用户排除的错误阶段三路线及其衍生成果，不作为本次答案或输入；不能将其与当前已经正式验收冻结的阶段三混为一谈。

### 4. 直接相关的旧工程文件

以用户指定的旧工程文件夹为只读范围，检查聊天节点、母版内容或已打开材料直接指向的相关文件。

允许沿具体疑问查看对应阶段中实际发现的相关对象，不局限于聊天逐字点名的文件。

但不允许：

- 因为进入一个文件夹，就查看其中所有文件；
- 因为发现一种问题，就推测整个旧工程都有同类问题；
- 把有边界查证扩大成旧工程全目录重扫。

### 5. 必要的用户语言和目标说明

可以使用已经正式保存、允许使用的用户交易语言、目标和历史说明，帮助理解原话。

这些材料不能代替六份聊天的完整阅读。遇到含义冲突，应回到原话及上下文；不能把失败候选、尚未接受的解释或后来形成的规则，倒写成早期用户原意。

也不因此自动增加对其他聊天窗口的全文扫描。

## 三、开始时怎样确认读的是同一批材料？

正式执行获得授权后，先确认本次采用的固定版本，包括：

- 两份母版；
- 六份聊天；
- 三个阶段的冻结成果；
- 已允许使用的辅助说明；
- 旧工程只读目录。

确认文件的实际位置和身份，避免同名不同版本混用。

对六份聊天，还要确认：

- 正文是否完整；
- 消息如何分界；
- 第一条和最后一条消息是什么；
- 每条消息对应原文件的什么位置。

消息中的转贴、引用和执行回报，不能被错误拆成新消息，也不能全部归为用户自己的判断。

这些信息直接放入本次详细依据中，不另建一套管理系统。

**文件完整、消息数量对得上，只能帮助确认阅读范围，不能代替逐条阅读和理解。**

## 四、第一步：两份母版怎样逐项对照？

### 1. 两份表分别读取

先分别检查两份母版，不能因为结构相似就只读一份，再推测另一份相同。

对排除指定两页后的全部工作表，检查：

- 实际使用区域和非空内容；
- 隐藏工作表、隐藏行列；
- 公式、保存结果及跨表引用；
- 来源说明；
- 必要的合并单元格和实际存储位置；
- 人工引用、主观内容及展示内容。

不需要逐格登记空白单元格，但不能漏掉实际保存的内容。

### 2. 区分“能力类别”和“具体交易记录”

例如：

> “记录尝试开仓过程”是一类能力；某笔交易的五次尝试，是这一能力下的五条具体记录。

两者都需要理解，但不能把记录条数、单元格数和能力数量混在一起。

相同事实在多个页面重复显示，可以合并解释，但必须保留出现位置，核对不同位置之间是否一致。

### 3. 每项内容实际查什么？

围绕实际内容查清：

- 它在说什么；
- 在哪份母版、哪个位置；
- 保存的是原始记录、计算结果、估算，还是其他内容；
- 有无公式，公式与保存结果分别是什么；
- 来源指向哪里；
- 本次实际核验到了什么；
- 还有什么无法确认。

来源是谁提供、结果是否估算、是否实际打开核验、还有什么不知道，是不同问题，不能用一个“可靠”等级代替。

### 4. 比较两份母版的变化

逐项确认是否存在：

- 内容相同；
- 改名、移动、合并或拆分；
- 新增或删除；
- 数据、来源或算法变化；
- 增加证据；
- 只改变展示；
- 结果冲突；
- 暂时无法确认对应关系。

不能因为后期母版更晚，就默认它更正确。

### 5. 与三个冻结阶段逐项对应

查清同一内容是否已经有：

- 组成部分和能力归属；
- 具体数据或零件；
- 来源和形成过程；
- 版本说明；
- 保留、限定使用、以后重算、参考、禁止或未决等处理记录；
- 用户认可范围和其他证据限制。

查不到同名记录时，先检查是否改名、合并、拆分或放在其他位置。

**此时形成的是初步对照判断。暂时未对应的，先记为“待核实的对应差异”，不能直接称为新增能力、构建输入或待解决问题。**

母版对照完成后，仍继续完成六份聊天的两遍扫描，不把这一结果作为决定“要不要全文扫描”的关卡。

## 五、第二步：完整正向扫描怎样做？

### 阅读方式

从 W01 第一条原消息开始，按原文件顺序连续读到 W06 最后一条原消息。

- 按连续消息分批读取。
- 长消息连续分段，不用摘要代替正文。
- 遇到截断，补齐缺失部分。
- 不因没有关键词而跳过。
- 一条消息涉及多件相关事情，分别理解和保留。
- 分清用户原话、当时聊天窗口的解释、转贴执行回报和工具内容。
- 时间标签存在疑问时，核查或保留疑问，不自行重新排列历史。

### 正向主要从什么角度理解？

正向重点查事情怎样形成：

> 用户为什么提出，当时是什么意思，计划怎样做，实际声称做了什么，形成了什么，后来怎样变化。

具体包括：

- 用户的交易术语、黑话和习惯表达，在当时语境中是什么意思；
- 哪些是讨论或建议，哪些是确认、授权或验收；
- 相关阶段用了什么数据和方法，产生什么文件和结果；
- 执行回报与实际文件能够证明的内容是否一致；
- 后来的修正、取消、替代是否传到后续成果；
- 对客观交易链提供了什么，留下什么限制。

不能只围绕母版已经呈现的内容阅读。**历史中有证据支持、但母版没有呈现的相关要求、数据和方法，同样要保留。**

每条消息都要实际阅读，并有最小覆盖记录；只有与本次判断有关的内容，才需要详细解释。不能把每条无关消息都做成长表单，也不能只登记“已读”而不理解正文。

## 六、两遍扫描和母版对照过程中，怎样同步查文件？

这不是最后再追加一次旧工程扫描，而是穿插在三项工作中的查证动作。

### 什么时候需要打开相关文件？

当一个与客观交易链直接有关的判断，需要实物才能确认时，例如：

- 聊天说某项结果已经产生、修正或验证；
- 用户说资料已补齐，而后续成果仍说缺少；
- 前后对数量、时间、来源、版本或用途的说法不一致；
- 母版有值或公式，但来源、计算方法没有说明；
- 需要确认某项算法或脚本实际做了什么；
- 已打开文件指向必要的上游来源或后续结果。

**出现文件名，不代表必须打开；落实重要事实，也不必先证明发生错误才允许查文件。**

### 每次怎样查？

按同一条简明顺序：

1. 说明要查清哪件事。
2. 找聊天或母版点名的对象、对应任务的输出位置。
3. 必要时检查同一阶段实际发现的直接相关文件。
4. 已查看内容指向其他阶段的必要来源时，沿这条具体关系继续查。
5. 足以回答当前问题后，结束这条回查。

一份文件可以支持多个相关判断，不必为了每个引用重复读取同一内容。

已有材料已经足以支持某项事实时，可以确认已有，不必机械重做相同的文件核验；出现影响该事实的新信息时，再定点核查。**这一做法不能减少六份聊天的两遍完整阅读。**

### 不同材料查到什么程度？

| 材料 | 实际检查内容 |
|---|---|
| 表格 | 相关记录、公式、保存结果、实际位置及来源关系 |
| 数据文件 | 相关编号、时间、数量、状态和来源 |
| 脚本、算法说明 | 相关输入、处理逻辑及输出，不运行业务重算 |
| 截图 | 相关原图和必要相邻证据，不只相信旧文字识别结果 |
| 阶段回报 | 当时声称做了什么，与实物能证明什么分开说明 |
| 不同版本 | 内容、来源和使用关系，不能只凭文件名或修改时间选版本 |

读取多少，应由当前问题决定。核对文件身份就能回答的，不必继续查全部内容；涉及实际计算逻辑的，也不能只核对文件名就宣布已验证。

找不到或证据不足时，说明实际查过哪里、缺少哪段依据。不能把“本次没有找到”写成“整个旧工程从来没有”。

## 七、第三步：完整反向扫描怎样做？

正向完成后，保留正向原判断及其依据。

然后从 W06 最后一条原消息开始，逐条反向处理，直到 W01 第一条原消息。**消息顺序反向，每条消息内部仍按正常语序理解，并补读必要上下文。**

反向同样覆盖全部消息，不能缩成：

- 只回看正向发现的问题；
- 只沿两份母版追来源；
- 只读最后成果；
- 只看关键词命中。

反向重点回答：

- 后期成果最早对应哪项要求？
- 最终使用的数据，最初怎样产生？
- 早期要求最后实现、取消、替代了，还是没有交代？
- 早期内容是否因改名、移位或展示变化而被忽略？
- 后来的修正是否真正进入最终结果？
- 用户局部认可或局部否定，有没有被扩大解释？
- 某项“无法确认”，究竟是缺材料、关系没连上、版本不明，还是当时没有查完？

遇到需要实物确认的内容，仍按前述方式查相关文件。

发现新证据时，分别说明：

> 正向原来怎样判断；反向又读到什么；为什么保留、补充或修正；最后仍有哪些不确定。

不能悄悄覆盖正向原记录。

同一执行窗口已经读过正向内容，不能把反向这一遍称为完全盲式独立检查。它是一遍完整、另外保留判断的反向复核。

## 八、三项工作结束后，怎样合验？

最后同时核对两个方向：

- **从母版往历史查：**已经呈现的内容，有没有来源和形成过程？
- **从历史往成果查：**有证据支持的相关要求、数据和方法，最后进入母版、其他成果，还是被明确取消、替代或保留为未决？

最终分别说明：

- 已经交代清楚；
- 材料已有，但对应关系没连清；
- 来源或证明不足；
- 存在具体冲突；
- 本次范围内仍无法确认；
- 经查证确有尚未进入现有记录的相关内容；
- 属于人工判断或纯展示，不应被算成新增客观事实。

一项内容可以同时存在几种情况。可以为总览选择一个主要结果，但不能因此删掉其他有效限制。

即使发现现有记录没有收录的内容，也只是本次查证发现，**不自动成为正式能力、构建输入、问题总账新增项或后续执行任务。**

## 九、最后形成什么结果，怎样检查？

### 只形成两部分成果

**第一部分：普通中文结果说明。**

让用户直接看懂：

- 两份母版实际具备什么；
- 三个阶段已经交代什么；
- 哪些只是没有连起来；
- 哪些存在具体冲突或证据不足；
- 哪些仍无法确认；
- 如需处理，下一步具体需要用户决定什么。

不能用技术代号、记录数量或文件数量代替解释事情本身。

**第二部分：本次逐项对应及详细依据。**

集中保存：

- 母版具体内容、位置和版本关系；
- 两遍实际阅读范围；
- 相关原话、上下文及来源身份；
- 回查文件、实际范围和查证结果；
- 正向、反向判断差异；
- 与三个冻结阶段的对应；
- 结论及证明限制。

不另建新的问题总账，也不把每条证据记录都算成一个问题。

这份详细依据只服务本次检查，不能取代原始材料或现有正式成果。普通中文说明必须与它一致；发生冲突时回到原始材料查清，不能默认哪一份文件更有权威。

### 由谁执行和检查？

- **当前 Work：**在获得授权后执行读取、文件查证和成果整理，对自己的输出进行检查，但不把自查称为第三方独立审查。
- **新 Chat：**检查候选是否符合用户语义、历史关系、证据和权限边界，回查实际可访问的重要来源。
- **用户：**确认方案、执行权限、允许写入范围、结果验收和后续处理。

这里说的是本次安排，不是永久绑定窗口。以后职责变化仍由用户决定。

新 Chat 通过既定的 GitHub 固定版本方式检查候选，不恢复反复粘贴整份正文的旧方式。它没有实际打开的本地文件，必须明确说明；不能把检查 Work 的记录说成已经独立检查原件，也不能把部分来源复查称为重新完成了两遍全文扫描。

### 什么情况下才算可以交给用户验收？

至少需要满足：

- 两份母版排除指定两页后的全部工作表已处理，没有凭印象跳过隐藏内容或实际记录；
- 能力类别与具体交易记录分清；
- 六份聊天正向、反向均完整读取，没有未补齐的截断或跳段；
- 重要判断能够回到原话及必要实物；
- 正反差异已经说明，没有只报告一致之处；
- 文件回查有明确对象和边界；
- 未确认事项及检查限度公开保留；
- 关键行号、单元格、公式、数值和来源名称已对照实际材料核对；
- 两部分成果的事实、数量和状态一致。

这里的“重要判断”，主要包括会影响能力是否存在、数据来自哪里、采用哪个历史版本、是否确有遗漏、是否与冻结记录冲突等结论，而不是每一句无关描述。

完整性记录不能成为免责说明：两遍仍须实际阅读、理解全部原消息。但也不能把记录齐全包装成绝对不会漏解的保证。

### 个别证据不足，不必停掉全部工作

某个文件找不到、历史版本不明、来源链断裂，或某项发现与冻结记录不一致，可以保留该项限制，继续其他能够可靠完成的已授权工作。

发现差异本来就在本次查证范围内，不能仅因发现差异就停止整个任务。

### 需要停止并报告的情况

- 核心输入身份不一致，无法确认应该读哪一版；
- 核心原文无法完整读取，缺失部分不能补齐；
- 继续查证需要超出已经批准的对象或范围；
- 关键材料不可访问，已使整体目标无法可靠完成；
- 当前窗口已无法可靠保持对任务、原话和判断依据的理解。

只影响一项时，停止该项；确实影响整个任务时，才停止整体工作。
