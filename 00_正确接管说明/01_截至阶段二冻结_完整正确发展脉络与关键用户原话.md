这份文件是给一个**不能跨窗口读取旧对话**的新 Chat 窗口看的历史与语义正文。它负责让新窗口真正理解：项目为什么开始，用户怎样描述自己的交易和最高目标，旧工程曾经做过什么，为什么已经停止，后来怎样通过恢复、双向扫描、定位比较和独立审计走到阶段一与阶段二冻结，原阶段三为什么产生、原本怎样设计，以及当前为什么仍然只能停在“理解和等待用户重新授权”的位置。

本文件交接的正式成果只到：

> 阶段一和阶段二均已由用户作出全局验收，并正式冻结关闭。

它另外保存原阶段三已经形成的正确设计，用于解释两套冻结底稿原本怎样衔接；不交接后来错误执行阶段三的过程和结果。

本文件不是新任务，不是执行授权，不是问题清单，也不是实时状态表。它会忠实保存原阶段三已经形成的历史设计，但这只是为了让接手者知道正确路线原本怎样衔接。读到任何历史授权、历史计划、旧文件名称或 Codex 回报，都只能理解为“当时发生过什么”，不能把它当成现在可以继续执行的命令。

阶段二冻结以后曾经产生过一条受到路线偏离、扩张和上下文污染影响的旧业务路线。本文件不带入那条路线的业务答案、问题数量、候选结论、检查结果、修补内容或执行安排。阶段二冻结以后，只有用户对最高目标、角色分工、授权边界、用户语言和正确接管方式作出的澄清可以进入本文件，并且必须明确标成“用户后来的澄清”。

新 Chat 第一次读完本文件后，只需要向用户证明自己已经理解，不得因此设计后续工作、指挥新 Work 或旧 Codex、读取旧工程、修改文件、重新计算、建立客观交易链或开始交易分析。

## 1．先分清五个目标根，不能混成一条路线

这里的“目标根”，指一项工作为什么存在、最终服务什么。它不是文件夹路径，也不是某个阶段名称。

### 1.1 用户最高最终目标根

用户明确坚持的最高最终目标是：

> **彻底改变。**

它规定所有下层工作的最高服务方向，但截至阶段二冻结，用户没有预先指定自己具体要改变心理、性格、情绪、行为、纪律、规则或其他哪一方面，也没有确定怎样衡量和验收“彻底改变”。

知道最高目标，不等于得到任何具体工作的执行权限。

### 1.2 旧工程历史目标根

旧工程曾把交易所数据、截图、人工复盘、客观交易链、行为和心理分析、交易规则、风险阻断、可视化、十笔样本、一百三十六笔扩展以及大量工程管理逐步连成一条很大的历史路线。

用户后来明确说：

> 旧工程已经属于旧的工程了，已经属于失败的工程了，旧工程不再运营了。

因此，旧工程只是一处历史现场。它留下的具体原始导出、截图、聊天、脚本、工作簿和派生数据，将来只有在用户针对某个具体问题另行授权后，才可能被定点核查。旧工程整体不能续跑，也不是当前权威运行工程。

### 1.3 阶段一和阶段二审计目标根

阶段一和阶段二是后来建立的两段独立历史审计：

- 阶段一审计 K01 正式启动以前的历史：历史上认为客观交易链需要什么，旧工程留下了哪些具体零件、来源、关系、限制和缺口。
- 阶段二审计 K01 正式启动以后的历史：计划过什么、实际做过什么、改过什么、出过什么问题、怎样返工或纠偏，以及留下哪些候选、限制和未决事项。

这两套审计基线已经冻结，但它们不是已经建好的客观交易链，也不表示候选已经采用。

### 1.4 当前接管目标根

当前只做一件事：让新的 Chat 窗口在不继承受污染的后续路线的前提下，准确理解截至阶段二冻结的项目历史、用户原话、术语、证据边界、角色和停点。

这只是接管和纠偏，不是业务阶段，不生产新的交易事实，也不决定以后具体怎么做。

### 1.5 原阶段三与今天的执行权限

原阶段三并不是空白。早在阶段一开始以前，用户与 Chat 已经把总任务分成三个阶段，并把第三阶段固定为：

> **阶段三｜客观交易链正式构成与构建输入最终交叉裁定。**

它原本要把阶段一的 K01 前冻结基线与阶段二的 K01 后冻结基线放在一起逐项比较，最终回答“客观交易链由什么组成、具体用哪些文件和数据、哪些要重算、哪些只能参考或禁止、哪些仍然未知”。它不直接复制文件、不重算业务、不建立一百三十六笔交易链，也不做正式交易分析。

后来错误执行的阶段三及其后续结果已经被用户排除，但这不等于原设计从未存在。必须同时保留两个事实：

1. 原阶段三的目的、输入、方法、交付和停止门已经设计过；
2. 当前没有阶段三执行授权，后来错误执行的过程和结果也不能继续使用。

如果用户决定继续，应先检查新 Chat 是否完整理解正确历史和原设计，再讨论当前是否具备进入阶段三的条件。只有用户再次明确授权，新的干净 Work 执行窗口才可以开始；不需要继续受污染的旧 Codex 线程，也不因读到历史合同自动开工。

## 4．四类内容永远不能互相冒充

| 内容 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 客观记录 | 可核对的委托、成交、仓位、资金、费用、价格和时间事实 | 用户当时为什么这样做，或用户的心理原因 |
| 用户原话 | 用户说过什么、怎样描述自己的经历、要求和术语 | 未经交易记录核验的交易所事实 |
| 人工复盘 | 用户历史上亲自填写的原因、判断和补充 | 可以被人工智能补写成客观事实的内容 |
| 人工智能解释 | 根据材料提出的理解、候选原因或建议 | 用户原话、客观事实、用户认可或用户授权 |

用户转发人工智能文字，不等于用户亲自认可其中每个判断；用户上传报告，不等于验收报告内容；用户继续讨论或没有反对，也不等于逐项技术认可。

### 11.5 原阶段三的执行方法

原设计不是再做一遍阶段一或阶段二，而是按下面顺序工作：

1. **先核验冻结身份。**阶段一、阶段二文件身份不一致就停止，不能在未知版本上比较。
2. **先从 K01 前向 K01 后检查。**逐项看原组件、能力、零件、生产关系和缺口后来被保留、修正、替代、只改展示、改算法、禁止还是仍未解决。
3. **再从 K01 后反向检查。**每个新增实现、问题、纠偏、算法变化和展示变化都必须找到它在最终客观链中的真实位置；“后来新出现”不等于“新增客观能力”。
4. **把差异分清性质。**至少区分同一事实、新实现、纠正旧实现、收窄范围、新增客观能力、新增后台支持、纯展示、需要重算、证明旧用途禁止、K01 前更强、需要定点核查、缺权威来源和语义层不同。
5. **只在必要时定点回源。**只有具体冲突、版本、选择范围、后继修正、算法输入或悬空来源需要确认时，才按冻结记录中的路径、文件指纹、工作表、范围、消息和生产关系查看原件；不得重扫 W01 至 W06 或 18.7GB 旧工程。
6. **按证据强弱裁定。**优先使用交易所原始导出、原始截图和原始行情；其次是能逐行回源的标准化数据，再其次是上游、方法和验证范围清楚的派生事实。文件更新、名称含“最终”、后继读取、检查通过和用户程序性确认都不能单独证明技术正确。
7. **分别裁定组件、能力、具体输入、生产关系、未知和缺口。**高层名称不能代替具体文件，文件存在不能代替具体工作表和字段可用，局部问题也不能扩大成整本文件错误。

| 可整份复制候选 | 以后经过用户验收并另行授权，可以按已核对的同一版本整份复制 |
| 只抽取指定部分候选 | 只能拿指定工作表、范围、字段、行或图像区域，不能把整件文件当权威源 |
| 回可靠来源重算候选 | 保留可靠上游和已确认的方法边界，但旧计算结果不能直接复用 |
| 仅供历史参考 | 只用于理解历史、比较版本、查看算法或追来源 |
| 明确禁止 | 精确禁止某个版本、字段、公式、算法、范围或用途，不能无依据扩大成整件都错 |
| 暂时未解决 | 当前证据不足，不能决定是否采用 |
| 必要但没有可靠零件 | 这项能力确实需要，但当时没有可用权威输入 |

以上都只是“待用户验收的最终裁定候选”。阶段三执行者不能自行把它们改成已经复制、正式晋升、正式准入或已获用户逐项接受。

### 11.7 复合工作簿、K08、K09、资金方法和 RW003 怎样处理

原设计明确禁止整本继承十九份复合工作簿。每本至少要分开看客观数据、派生结果、身份映射、算法口径、字段语义、用户人工内容、产品结构、页面展示、审计版本血缘和十笔到 136 笔扩容。

它还要求单独处理容易混淆的历史重点：

- K04、K05 的很多内容是既有能力的新实现或接口，不自动成为新增高层能力；
- 405 个技术持仓阶段到 210 个用户阶段的聚合，需要判断是客观链必需能力、后台支持还是展示聚合；
- K08 必须分开客观持仓修正、规则修正、页面产品和用户本人验收缺口；
- K09 必须分开可以抽取的 136 结构、必须禁用的具体公式、时区和保护问题，以及未传播的后继修正；
- RW003 只能在已证明的十个数值类型修正、三个“持仓期间”标签、有限用户页面改善和十笔范围内使用，不能整本升级成 136 笔母版或全算法通过；
- 资金事件、快照估值、条件模型、实际余额、实际账户权益、未实现盈亏和展示口径必须分开；
- 被用户否定的页面，与同一任务中可能独立有用的映射数据必须分开；
- 已经丢失的历史字节不得补造。

### 11.8 原阶段三应交付什么，用户验收什么

原设计要求形成七项成果：总核对清单、最终客观交易链组成与能力清单、K01 前后逐项交叉裁定总账、最终构建输入准入与复用处置清单、最终权威来源／生产关系／版本边界矩阵、用户白话验收总览和机器索引。

用户白话总览必须让用户不读机器索引也能直接看懂：

- 客观交易链到底包含什么；
- 每个部分由哪些关键文件和数据提供；
- K01 后改变了什么；
- 哪些已准备、需重算、可留空或被阻断；
- 哪些只能参考、禁止或仍然未知。

用户负责验收的是人工智能对用途、范围、版本、风险和限制的理解是否符合项目目标，不是亲自检查源码、文件指纹、上万行数据或逐个公式。即使七项成果形成，阶段三也只能停在“等待用户验收”，不能自行宣布最终冻结。

### 11.10 必须排除的后来错误路线
